# Что можно улучшить

Разбор проекта «со стороны»: что болит сейчас, какие фишки дадут больше всего
пользы на единицу работы и чего не хватает инженерно. Отсортировано по
соотношению «польза / трудозатраты».

Легенда сложности: 🟢 вечер · 🟡 несколько вечеров · 🔴 крупная работа.

---

## 0. Что сломано или рискованно прямо сейчас

### 0.1 Бот молча теряет группы 🟢
В последнем `docs/data/meta.json`: `"fetched": 1, "failed": 75, "groups": 74`.
Семьдесят пять неудачных загрузок — и никакого сигнала: workflow зелёный,
сайт показывает старые данные, человек видит «пар нет» и считает, что их нет.

**Что сделать**
- В `fetch_all.py` — выход с ненулевым кодом, если `failed / total > 0.2`
  (порог флагом `--fail-threshold`), **после** записи уже скачанного.
- В workflow — шаг, который при деградации создаёт/обновляет issue
  (`gh issue edit` по метке `bot-health`), а не просто краснеет.
- На сайте — строка в баннере: «часть групп не обновилась: N».

### 0.2 Нет наблюдаемости 🟢
`meta.json` уже содержит всё нужное, но его никто не смотрит.
Страница `#/status`: когда последний успешный прогон, сколько дней
опубликовано, доля ошибок, размер зеркала, график «свежесть по датам».
Плюс бейдж в README из того же JSON (shields.io `dynamic/json`).

### 0.3 Монолит `static/index.html` — 2500 строк 🟡
Разметка, стили и вся логика в одном файле. Любая правка — это поиск по
тексту, а тесты вынуждены грузить страницу целиком. При этом склейка в один
файл — хорошее свойство (PWA, офлайн, без сборщика).

**Компромисс:** `static/src/{state,api,render,calendar,search,pwa}.js` +
`tools/build.py`, который инлайнит их в `index.html` (простая конкатенация с
маркерами `<!-- #include -->`, без npm). CI проверяет, что собранный файл
совпадает с закоммиченным.

### 0.4 Кэш service worker без версионирования содержимого 🟢
Проверить, что `sw.js` использует имя кэша с хэшем билда, иначе у части
пользователей после деплоя остаётся старая оболочка с новым форматом данных.
Добавить «обнаружено обновление — перезагрузить» тост.

## 1. Фишки, которых реально не хватает

### 1.1 Push-уведомления 🔴 (но это киллер-фича)
Главная причина открыть расписание — узнать, что **изменилось**. Сейчас за
этим надо заходить самому.

- «Через 10 минут пара: Матанализ, 233» — локально, без сервера:
  `Notification` + `setTimeout`/`showTrigger` при открытой вкладке,
  периодический `periodicSync` в Android-Chrome.
- «Завтра в расписании появилась замена» — уже нужен push-сервер.
  Дёшево: бесплатный воркер (Cloudflare Workers / Deno Deploy) хранит
  подписки, бот после прогона шлёт diff. ~100 строк.

**Промежуточный шаг за вечер:** Telegram-бот (см. 3.1) — те же уведомления
без Web Push и без iOS-ограничений.

### 1.2 Подписка на календарь вместо экспорта 🟡
`.ics` сейчас — разовая выгрузка: расписание поменялось, а в календаре
старое. Нужен **фид**: `docs/data/ics/<groupId>.ics` (и вариант с подгруппой
`<groupId>-1.ics`), который бот перегенерирует вместе с данными. Ссылка
`webcal://` — Google/Apple подтягивают сами раз в несколько часов.
Стоимость: один новый генератор в `fetch_all.py`, вся логика `.ics` уже есть
на фронте — вынести в Python.

### 1.3 «Что изменилось» 🟡
У нас есть история git по каждому дню — это бесплатный журнал изменений.
Бот может складывать `docs/data/diff/<date>.json`: пара добавлена, убрана,
сменился преподаватель/аудитория/тема. На сайте — лента «изменения за
сегодня» и жёлтая метка на изменившейся паре с подписью «было: 233 → стало:
on-line, 2 часа назад». Это ровно то, за чем студенты ходят в таблицу замен.

### 1.4 Персональное расписание 🟡
Сейчас фильтр ограничен подгруппой. Добавить:
- скрытие конкретных пар/предметов (практика, физра по справке);
- свои заметки к паре (localStorage, экспорт в тот же `.ics`);
- «мои преподаватели» — быстрый доступ к их консультациям;
- профиль одной строкой в URL (`#/p/<base64>`), чтобы перенести на другое
  устройство без аккаунтов.

### 1.5 Поиск по неделе, а не по дню 🟢
`x/<date>.json` уже есть на каждый день окна — достаточно пройтись по 7–14
файлам (они маленькие и закэшированы). Запросы «когда физика на этой неделе»,
«все окна у СА-231б», «свободна ли 233 в четверг в 10:00».

### 1.6 Поиск свободных аудиторий 🟢
Инверсия `x/<date>.json`: аудитория × пара → занято/свободно. Полезно
старостам и преподавателям, уникально для этого сайта.

### 1.7 Статистика 🟡
По неделе/месяцу: часов по предметам, самый тяжёлый день, количество окон,
доля онлайн-пар, сколько пар заменено. Красиво, шарится, стоит один проход
по уже скачанным JSON.

### 1.8 Сравнение групп 🟢
Две-три группы рядом — «когда у нас совпадают окна». Данные те же, нужен
только второй столбец в рендере недели.

### 1.9 Виджеты и шеринг 🟢
- `?/og/<group>/<date>.png` — картинка дня для отправки в чат. Без браузера
  можно рисовать PNG тем же кодом, что `tools/make_icons.py`.
- Кнопка «скопировать день текстом» (уже есть для домашки — расширить).

## 2. Качество интерфейса

- **Скелетоны вместо пустоты** при загрузке дня — сейчас видно мигание.
- **Оптимистичная навигация:** соседние дни недели префетчить заранее
  (`link rel=prefetch` или просто `fetch` в idle) — свайп станет мгновенным.
- **Виртуализация списка групп** не нужна (80 элементов), а вот
  **нечёткий поиск** по группе (`са231` → `СА-231б`) — да.
- **Пустые состояния с пользой:** вместо «не опубликовано» показывать
  расписание той же пары недели неделей раньше с пометкой «предположительно».
- **Доступность:** проверить порядок фокуса в модалках и объявление смены
  дня через `aria-live` (сейчас часть есть, нужен аудит целиком).
- **Печать:** `@media print` — расписание недели на один лист A4.
  Старосты печатают, это две дюжины строк CSS.
- **Тема:** кроме светлой/тёмной — контрастная и «эконом» (без аурор) для
  слабых телефонов; аврора уже оптимизирована, но выключателя нет.

## 3. Платформа

### 3.1 Telegram-бот 🟡
Данные статические и публичные — бот может быть полностью serverless:
GitHub Actions раз в полчаса после прогона шлёт подписчикам diff через
Bot API, подписки хранятся в отдельной ветке/Gist. Команды:
`/today`, `/week`, `/who Зинкин`, `/room 233`, `/sub СА-231б 1`.
Для аудитории техникума это, вероятно, более живой канал, чем PWA.

### 3.2 Открытый API 🟢
То, что лежит в `docs/data/`, уже является API. Нужно только:
`docs/data/openapi.json` (или просто раздел в README), CORS уже даёт Pages,
и версионирование формата (`"v"` в дне уже есть — зафиксировать правила).

### 3.3 Защита от смены вёрстки almetpt.ru 🟡
Парсер держится на классах (`changesPair`, `Staff`). Стоит:
- «канарейка» в CI: раз в сутки качать живую страницу и сверять с ожидаемой
  структурой (не содержимым) — ломается раньше, чем ломаются данные;
- авто-обновление фикстур `tests/fixtures/raw/` через workflow с PR.

### 3.4 Размер репозитория 🟡
`docs/data/d/**` коммитится каждые 30 минут — история растёт вечно, а
фотографии преподавателей это ещё ~4 МБ бинарников. Варианты: хранить данные
в отдельной ветке `data` с периодическим `git checkout --orphan` (squash
истории), или публиковать через Pages artifact вместо коммитов.

### 3.5 Производительность доставки 🟢
- `summary.json` отдавать в сжатом виде/укоротить ключи — он грузится всегда.
- Хэш в имени файла данных + `immutable` кэш, а `meta.json` — `no-cache`.
- Preconnect/preload для шрифтов и первого запроса данных.

## 4. Инженерная гигиена

- **CI на каждый PR:** сейчас тесты гоняются только в боте. Нужен отдельный
  `ci.yml` (python-тесты + jsdom-тесты + проверка сборки статики).
- **Линтеры:** `ruff` для Python, `eslint`-минимум для фронтенда — обе вещи
  ставятся одной строкой и ловят то, на что сейчас уходят ревью.
- **Типы:** аннотации + `mypy --strict` на `parser.py` (самый хрупкий модуль).
- **Фикстуры времени:** тесты зависят от «сегодня» — вынести часы в
  инъектируемый объект, чтобы прогон был детерминированным в любой день.
- **Конфиг вместо констант:** базовый URL, TTL, окно дат — в один
  `config.py`/`.env`, сейчас разбросано по `fetch_all.py`.
- **`CONTRIBUTING.md` и шаблоны issue** — проект достаточно взрослый.
- **Лицензия** — её нет вообще; без неё формально нельзя ни форкнуть, ни
  использовать. MIT + дисклеймер о принадлежности данных техникуму.

## 5. Порядок, в котором это стоит делать

1. **Неделя 1 (надёжность):** алерт при `failed`, страница статуса, лицензия,
   CI на PR. *Маленько работы — сразу перестаём терять данные молча.*
2. **Неделя 2 (видимая польза):** ICS-подписка, поиск по неделе, свободные
   аудитории, печать.
3. **Неделя 3 (главное):** диффы расписания → уведомления (сначала Telegram,
   потом Web Push).
4. **Дальше:** модульная сборка фронтенда, персональный профиль, статистика.
